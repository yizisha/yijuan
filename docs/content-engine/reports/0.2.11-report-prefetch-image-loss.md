# FlowReader — 0.2.11 报告（修复：有的插图要退出重进才显示）

日期：2026-09-11。触发：用户装 0.2.9/0.2.10 后反馈
**「有的直接就能加载，有的还需要我退出去之后再进来才能加载」**，并附两张真机截图。

版本 **0.2.11**（versionCode **5684**）。

---

## 0. 先纠正一个误读（它决定了排查方向）

截图里那个"虚线方框 + OBJ 字样"**不是我们的损坏占位图**，而是字体对 **U+FFFC
（OBJECT REPLACEMENT CHARACTER）的默认字形**。

⇒ 它的含义是「**这一章根本没有生成图片块**」，而不是"资源缺失/解码失败"。
如果是我们的占位，会是一个 BrokenImage 图标（`ReaderImage` 的 else 分支）。

同时确认：**0.2.10 的路径泄漏修复生效了** —— 两张截图都不再有 `[IMG:/data/…` 文字。

---

## 1. 设备取证（不猜）

用设备自带 sqlite3 与包内文件核对那本《谁让他修仙的！》（1434 章，publicationId `c67d674b…`）：

| 事实 | 值 |
|---|---|
| `manifest.json` | 1,306,160 字节；documents=1435、sections=1434、resources=**9** |
| resources 媒体类型 | 1 × image/jpeg、8 × image/png |
| 出问题那节的标题 | **作品相关**（ordinal 2） |
| 该节的 range | `OEBPS/Text/Section0002.xhtml` `[0, 11)`（文档长度 12） |
| 该文档的图片 | 1 张：`offsetUtf16=5`、`containerPath=OEBPS/Images/vol.png`、`raw=../Images/vol.png` |
| 资源文件 | `OEBPS/Images/vol.png` → `resources/8483071ca6ca…`，**存在，249,255 字节** |

⇒ 资源在、路径匹配、偏移也落在 range 内。**解析链路没问题，问题在排版与缓存。**

## 2. 根因：预排版把图片"算进了缓存键"却没有"用来排版"

`PagedReader` 里相邻章预排版的原始代码是：

    val neighbourImages = ...                                   // ← 我写成了下面这行的内联调用
    val neighbourKey = pageKey.copy(
        ...
        imageKey = imageKeyOf(loadImagesForPagination(target))   // 键里带了图片指纹
    )
    if (pageCache.get(neighbourKey) != null) continue
    val neighbourPages = withContext(paginationDispatcher) {
        val neighbourBlocks = buildChapterBlocks(neighbour.title, neighbour.content, indentEnabled)  // ← 没传图片！
        paginator.paginate(neighbourBlocks, pageHeightPx, gapPx)
    }
    pageCache.put(neighbourKey, neighbourPages)

`buildChapterBlocks` 的 `images` 参数**有默认值 `emptyList()`**，所以这行既不报错也不明显。
后果：

1. 预排版产出一份**没有图片块**的页列表，却用"**有图片**"的键缓存起来；
2. 用户顺序翻到下一章 → `goToChapter` 正常加载了图片 → 键**完全一致** → **命中缓存**；
3. 于是沿用了那份没有图的排版 → U+FFFC 原样留在文本里 → 字体画出 OBJ 方框。

**这正是"有的好、有的要退出重进"的原因：**

- **顺序翻章**（走预排版）→ 命中坏缓存 → 只显示方框；
- **从目录直接跳章**（现算，不走预排版）→ 正常显示图；
- **退出重进** → 该条目被 LRU（容量 6）淘汰 → 重新排版（这次带图）→ 图出现。

---

## 3. 修复

1. **预排版必须把图片一起用于排版**：先取 `neighbourImages`，用 `imageKeyOf(neighbourImages)` 组键，
   并把同一个列表传给 `buildChapterBlocks`。
2. **删掉 `buildChapterBlocks` 的 `images` 默认值**，让**编译器**强制每个调用点显式表态。
   这是本项目已有的教训做法（HANDOFF §6 第 14 条附近：`flattenToc` 的危险默认值曾导致
   「所有目录项 sectionId 全为 null」），本次缺陷是同一类错误：
   **"可选默认值"掩盖了"必须一起决定的参数"**。删除后，

       e: No value passed for parameter 'images'.

   立刻把预排版那处漏传挡在编译期（本次确实先编译失败再修好，见第 4 节）。

## 4. 验证

- 删默认值后**编译立即失败**在 4 处旧调用（含测试），逐个补上显式 `images`；
  这证明"漏传"从此不可能再发生。
- 既有回归测试（`PagedReaderImageBlocksTest`）继续覆盖：
  U+FFFC → 独立图片块、偏移连续、被切开标记报"放不下"、缺失资源仍占位、无图时不插入。

## 5. 附带的性能观察（**未在本批优化，如实记录**）

`ChapterImageResolver` 需要 section 范围与资源路径，目前靠**解析整个 revision 的
`manifest.json`**（本书 **1.3 MB**）来得到。它按 revision 缓存（LRU 3），
但**第一次**打开该书时的第一次换章要现场解析 1.3 MB JSON（真机估计数百毫秒到 2 秒），
因为换章时旧章仍留在屏幕上，表现为"点了没立刻动"而不是转圈。

**更省的做法**（下一批可做，不必现在动）：

- section 范围改从 Room `reading_sections` 按 ordinal 取（已建索引，单行查询）；
- 文档 JSON 路径可由 `documentKey` 直接推导（`documents/<sha256(documentKey).take(32)>.json`，
  即 `PublicationStore.fileNameFor`）；
- 只剩 resources 需要 manifest —— 可只解析一次并持久缓存，或把「containerPath → relativePath」
  写进文档 JSON 自身（那样连 manifest 都不用读）。
