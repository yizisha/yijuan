# FlowReader — 0.2.6 / 0.2.7 报告（跨章节切换卡顿、「本章暂无内容」误报、本机 FTS5 缺失）

日期：2026-09-11。触发：用户反馈「跨章节很卡顿，要加载挺长时间，无法丝滑阅读，加载时还会显示本章暂无章节」。

版本：**0.2.6（versionCode 5679）** 与 **0.2.7（versionCode 5680）**。
两批在同一次会话内完成，0.2.7 只新增「本机 SQLite 缺 fts5」的诚实处理（第 5 节），
因此合并成一份报告；设备上最终安装的是 **0.2.7**。

---

## 0. 症状与复现路径

用户处于**默认分页模式**（`ReadingSettings.pageMode` 默认 `PageMode.PAGED`，
见 `domain/.../ReadingSettings.kt:210`），因此每次换章都走 `PagedReader`：

1. 点下一章 → 整屏换成居中转圈（不是章节内容）；
2. 等一段时间；
3. 短暂闪出 **「本章暂无内容」**；
4. 正文才出现。

即「转圈 → 错误空态 → 正文」三段式，正是「加载挺长时间 + 显示本章暂无章节」。

### 0.1 真机实测的书籍规模（用于判断「慢」在哪）

用设备自带 sqlite3 只读查询 `databases/flowreader_db`（4 本书）：

| bookId | 格式 | 章数 | 正文总字符 | 单章最大字符 |
|---|---|---|---|---|
| 1 | TXT | 491 | 2,436,475 | 7,999 |
| 2 | EPUB | 1,434 | 3,049,992 | 4,145 |
| 3 | EPUB | 9 | 114,325 | **39,168** |
| 4 | TXT | 907 | 4,058,845 | 7,999 |

结论：单章 8 KB 量级（第 3 本有一章 39 KB）。**单章排版本身是几十毫秒量级，
不足以解释「挺长时间」**；「慢」主要来自「每次换章都把阅读器整块卸掉重建」这件事本身，
以及每一章都要从零量一遍的新感知成本（第 1 节 R1–R3）。

## 1. 根因（均已定位到代码）

### R1 换章时把整个阅读器卸载掉（观感 = 重新加载）

`goToChapter` 进入时写 `isLoading = true`，而 `ReaderScreen` 用同一个 `isLoading` 驱动
`FlowStateHost`（`ReaderScreen.kt:239`）。`FlowStateHost` 在 `isLoading` 为真时
**不渲染 content 分支**（`FlowStateHost.kt:67-71`），整个阅读器被卸载、换成居中转圈。
换章本来只是「读一章正文」，却被表达成「整本书重新打开」。

### R2 每次换章都重建阅读器，排版结果全部丢弃

    key(uiState.scrollRequestVersion, settings.pageMode) { ... }   // ReaderScreen.kt:251

`goToChapter` 成功时 `scrollRequestVersion` +1。`key()` 一旦变化，该子树内**所有 remember
状态被丢弃**——包括已经算好的分页结果。回到刚看过的章节也要重新量。

### R3 「还没排版」被当成「这一章是空的」（空态误报的直接原因）★

`PagedReader` 原来用 `produceState(initialValue = emptyList(), ...)` 持有分页结果，
紧接着 `if (pages.isEmpty()) Text(R.string.reader_chapter_empty)`。
而 R2 保证了这个初值**每次换章都会重新出现**。于是只要排版没跑完，
界面就笃定地宣告「本章暂无内容」。
**「尚未计算」与「算出来是空」是两个状态，原实现合并成了一个。**

### R4 相邻章正文预取窗口偏窄且顺序不优先

`BookLoader.preloadChapters` 顺序为 `[-1, +1, -2, +2]` 再 `.take(3)`（**丢掉 +2**，
且最需要的「下一章」排第二）；`CacheManager.MIN_CHAPTERS_PER_BOOK = 2`，
刚预取进来的相邻章很容易被自己挤掉。

### R5 每次打开书都整本重建全文索引

`indexBookForSearch` 每次打开都 `deleteBookContent` + 逐章重写 FTS；
且因缺少「是否已索引」的记录，无法跳过。0.2.4 只把它从「逐章查库」改成「分块批量」，
没有消除「每次都做」。

## 2. 修复（0.2.6）

### 2.1 换章不再卸载阅读器

新增 `ReaderUiState.isChapterSwitching`：

- `isLoading` 只用于**打开书本身**；
- `isChapterSwitching` 用于**书内换章**，不参与 `FlowStateHost` 分支 →
  **上一章留在屏幕上**，直到新章正文就绪后原子替换；
- 连点换章仍被去重（保留原 `isLoading` 的去重语义）；
- 换章失败清除该标志并提示（不会卡死在「换章中」）。

### 2.2 「尚未排版」与「空章」分离

新增 `PageRenderState` + `pageRenderState(pages)`（`ReaderPageCache.kt`）作为唯一判据：

| 状态 | 条件 | 界面 |
|---|---|---|
| `TYPESETTING` | `pages == null` | 「正在排版…」（`reader_chapter_paginating`，已补 9 个语言） |
| `EMPTY` | `pages.isEmpty()` | 「本章暂无内容」 |
| `PAGES` | 有页 | 正常分页 |

**只有真正算出来是空**才显示空章提示。

### 2.3 排版结果缓存

`ReaderPageKey` = 书 + 章序号 + 正文字长 + 正文哈希 + 标题 + 排版设置 + 字体 + 内容宽/高/段距。
容量 6 的 LRU，被提升到 `ReaderScreen` 的 `key(scrollRequestVersion)` **之上**
（`ReaderScreen.kt:113`），换章重建阅读器时它能幸存；正文/字号/字体/几何任一变化即自然失效。

### 2.4 相邻章预排版

当前章排版完成后，后台读取并排版**下一章优先、再上一章**，结果进同一个缓存。
翻到下一章时 `pageKey` 命中 → 同步拿到页列表 → 无闪空、无需等待。

### 2.5 预取窗口与缓存下限

- `preloadChapters` 改为 `[+1, -1, +2, -2]` 且 `PRELOAD_LIMIT = 4`；
- `MIN_CHAPTERS_PER_BOOK` 由 2 提到 4（否则刚预取的下一章会被当场挤掉）。

### 2.6 跳过无变化的全书重索引

`FullTextSearch` 新增持久表 `indexed_books(book_id, fingerprint, updated_at)`。
指纹 = 「章数 + 库中正文总长」；命中即跳过重建。指纹在**索引锁内、写完索引之后**记录，
崩溃半途不会留下「声称已索引」的假状态；指纹查询异常时退回旧行为（每次都重建）。

## 3. 未修复 / 明确遗留（不猜、不假装）

1. **S5 图片渲染仍 NOT_RUN**：新导入 EPUB 的插图依然不显示（`ImageBlock` 的 `U+FFFC`
   在 UI 层无渲染器）。本批未触碰。
2. **打开书时的逐章 N+1 仍在**：`ReaderViewModel.kt:531` 的 `resolveStoredLocator` 会把
   **每一章正文全部读出来**拼一份合成清单；而 `ContentLocatorResolver.resolve` 实际只在
   `ContentLocatorResolver.kt:62` 为目标文档调用一次 `documentProvider`。
   在第 0.1 节的规模下这是 **491–1434 次无谓正文读取**（打开书时同步等待），是本机
   「打开书慢」目前最大的单点。**本批没改**；**已在 0.2.8 修复**，
   见 `0.2.8-report-open-cost-and-s5-safety.md`。
3. **首章/跳章仍会走一次「正在排版…」**：只有相邻章被预热，目录跳到任意章仍需现场排版。

## 5. 额外发现（0.2.7）：本机 SQLite 没有 fts5 模块

验证 0.2.6 安装后启动时，logcat 出现：

    E FullTextSearch: android.database.sqlite.SQLiteException: no such module: fts5 (code 1 SQLITE_ERROR)
    E ReaderViewModel: com.flowreader.app.util.FtsException: Failed to initialize FTS database

进一步取证（均在设备上只读执行）：

1. 设备自带 `sqlite3 3.44.5` 执行 `CREATE VIRTUAL TABLE t USING fts5(x)`
   → `Error: stepping, no such module: fts5`；
2. 应用自己的库 `databases/flowreader_fts.db` 里 `sqlite_master` **只有**
   `android_metadata` 与 `book_content`（及一个自动索引、`sqlite_sequence`）——
   **`book_content_fts` 虚拟表与三个触发器从未被创建**；
3. `book_content` 里已有 **1398 行**（老版本`initialize()` 曾在建表失败后留下已打开的
   `database`，后续调用因早退而「成功」，于是正文行被写进普通表）。

⇒ 在这台设备上 **全文检索从来没有真正工作过**：书内搜索与全局搜索都不可能命中，
而书内搜索的失败被 `searchInBook` 的 catch 吞掉，只表现为「没有结果」。

### 5.1 顺带修掉的结构性缺陷

- `createTablesAndTriggers` 把 `indexed_books` 建在 **fts5 建表语句之后** → 该语句一抛异常，
  后面全部不执行，**2.6 的「跳过重建」在这台设备上其实一直没生效**。
  真机已验证：修复前 `sqlite_master` 里没有 `indexed_books`，修复后它出现了（而 fts 表依然不存在）。
  现改为**先建状态表**，再用 `createFtsObjects()` 单独尝试 FTS5 建表并捕获失败；
- 新增 `FullTextSearch.isFtsAvailable`（每进程在建模时确定一次）；
- `search` / `searchAll` 在不可用时抛新的 `FtsUnavailableException`（消息即原因）；
- `indexBookForSearch` / `SearchRepositoryImpl.rebuildIndex` 在不可用时**直接跳过写入**
  （写了也读不到，纯 I/O）；
- `searchChapters` 在重建**之前**失败，避免先做一次全库重建再报错；
- 书内搜索在不可用时给用户**明确提示**「本机数据库不支持全文检索（SQLite 缺少 fts5 模块）」，
  不再显示成「没有结果」。
- 建表每进程只尝试一次（`initialize()` 首次调用），因此**每次冷启动只会出现一次**该异常日志
  （带栈，E 级）与一条说明性警告，不再是每次操作都报。**未把它降级为静默**：这台设备真的没有该能力，
  留一条可检索的记录比无声失败好。

### 5.2 未完成的部分

**全局搜索页（`SearchScreen`）只显示 `搜索失败: <FtsUnavailableException 消息>`**，
没有做成专门的空态；本批未改 UI。要让本机真正能搜索，需要一条不依赖 FTS5 的检索通路
（例如对 `book_content.content` 做 `LIKE` 扫描 + 复用 `SearchHitProjector` 投影定位）。
