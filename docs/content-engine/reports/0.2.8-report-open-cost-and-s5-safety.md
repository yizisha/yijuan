## 1. 先纠正记录：S5 的插图呈现**没有**做完

用户的前提是「S5 做完了」。代码事实不支持这个结论（2026-09-11 23:2x 核对）：

| 证据 | 事实 |
|---|---|
| `PublicationStore.resourceIndex()` | 自述为「S5『图片呈现』正确修法的**基础件，当前尚无调用方**」，全工程**零调用** |
| `PublicationStore` / `PublicationImportCoordinator` 的引用 | 只有 DI 构造（`AppModule.kt:290`）与**导入路径**（`BookImporter` / `BookParser`） |
| `ImageBlock` / `resourceRefs` 在 UI 层 | **零命中**；只有解析器与清单构建器在用 |
| `U+FFFC`（图片在规范源文本里的占位符） | 只出现在解析器、清单构建器、`PublicationStore` 注释里，**UI 层没有任何渲染** |
| 图片渲染器文件 | 除「阅读背景图」外**不存在**任何 Image 渲染组件 |
| 现有渲染路径 | `PagedReader` / `ReaderContent` 仍只认旧标记 `[IMG:路径]`，而新导入路径已不再产生该标记 |

⇒ **新导入的 EPUB 插图在阅读界面依然不显示**（与 HANDOFF §4.2 的原判断一致）。
0.2.5 那次真正落地的，是把「结构化正文 + 资源落盘 + 分片」的基础件写好（`PublicationStore`
的 `stage/commitFiles/resourceIndex`）以及章节读取的批量查询改造 —— **都是导入/打开路径**。

### 1.1 所以「S5 把卡顿带回来」的真实机制是什么

不是 S5 的代码在换章时跑了什么，而是：

- 你在 0.2.5 那次导入并开始读的是**新导入的 EPUB**（真机 book 2：**1434 章**）；
- 阅读器本身的换章机制（整屏转圈 + 误报「本章暂无内容」+ 每次从零重排）与书的规模无关，
  但**书越大，打开书的代价越高**——打开时的逐章 N+1 在 1434 章的书上要读 1434 次正文；
- 两者叠加，就是「试了一次 S5 之后明显变卡」。

**结论**：换章机制已在 0.2.6/0.2.7 修好；本批把「打开书」这条规模相关的路径也修好，
并用测试钉死成本契约 —— 这才是「别把卡顿带回来」的可验证做法。

## 2. 打开书的逐章 N+1（本批修复）

### 2.1 缺陷

`ReaderViewModel.resolveStoredLocator` 为了拿「每章正文长度」把**每一章正文**都读出来
（真机 1434 章 = 1434 次正文读取，且发生在**打开书的同步路径**上，读完才显示内容）。
但 `ContentLocatorResolver` 实际只在 `ContentLocatorResolver.kt:62` 为目标文档取一次
`documentProvider` / `textProvider`。

即：**读过的东西，99.9% 从未被用过**。

### 2.2 修法（保持行为等价，只去掉无用读取）

- 新增 `ChapterDao.getChapterTextLengths(bookId)`：**一次聚合查询**取每章
  `LENGTH(content)`（`ChapterTextLength(chapterIndex, lengthUtf16)`），**不加载正文**；
  - 经 `ChapterRepository.getChapterTextLengths` 暴露（实现不得读正文，接口已注明）。
- `resolveStoredLocator` 只为**恢复器真正可能查阅的那一章**读正文：候选来自 locator 的
  `documentKey` 与 `sectionId`（最多 2 章，按
  `ContentLocatorResolver.findDocumentKey` 的「最后一段路径」语义解析，保证候选集是旧行为的超集）。
- **精确性不打折**：已加载正文的那一章用真实 `.length`（UTF-16）覆盖聚合查询的长度，
  因此 Tier-1 的边界判断仍然精确；只有「与 locator 无关的章节」才使用 SQLite 字符数
  （中文正文两者一致，差异只在含补充平面字符时出现，且只影响夹取上界）。
- 查询失败时长度退化为 0：只影响无关章节的夹取上界，**不会**丢掉用户位置。

结果：打开一本 1434 章的书，正文读取从 **1434 次**降到 **≤ 2 次**。

## 3. 把「成本与书规模无关」钉成测试（防 S5 回归）

新增 `ReaderChapterLoadCostTest`（2 项），不测「快不快」，只测**规模无关性**：

| 测试 | 断言 |
|---|---|
| `openingABookDoesNotReadContentForEveryChapter` | 同一本 20 章的书与 2000 章的书，**打开时的正文读取次数必须相等**，且 ≤ 4 |
| `switchingAChapterReadsOnlyTheChapterBeingOpened` | 同一动作在 20 章与 2000 章的书上换章读取次数相等，且**恰好 = 1 章** |

这两项一起构成对「尝试 S5 就把卡顿带回来」的直接防线：

- 若将来为图片呈现而在打开书时把全章结构/图片索引读一遍 → 第一项变红；
- 若把图片/资源解析放进换章路径（哪怕是同步 `documentProvider` 之外的额外读取）→ 第二项变红。

> 诚实说明：这两项锁定的是**正文读取次数**这一可计数指标，不是耗时。
> 真实耗时还会受设备 I/O、排版与解码影响；解码/图像缓存上限（主计划 §11.2）
> 在真正做 S5 时必须另行约束并做真机测量。

## 4. 顺带记录：一处既有坐标不一致（**本批未改**）

`buildCurrentLocator` 持久化的 `documentKey` 用的是 **`chapter.index`（物理章号）**：

    val docKey = currentChapter?.let { "chapter:${it.index}" } ?: "chapter:$chapterIndex"

而 `resolveStoredLocator` 合成清单里的键是 **`chapter:<读序>`（列表下标）**：

    val chapterDocKey = "chapter:$ordinal"

EPUB 出现跳号时两者不相等 → `findDocumentKey` 精确匹配失败、后缀匹配也失败 →
**Tier-2（上下文/锚点匹配，最精确的恢复级）被跳过**，只能落到 Tier-3（sectionId 百分比）。
后果是恢复精度降级（不是错位）。修它需要统一两者的坐标口径，会改变恢复行为，
必须单独一批 + 真机补验，**本批刻意不动**。
