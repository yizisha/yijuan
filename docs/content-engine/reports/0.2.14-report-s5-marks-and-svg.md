**缺陷 1（真 bug，本批新功能）：注音被画进基字内部、与基字重叠**

- 现象：`漢字`/`振仮名` 上方的注音**确实渲染了**，但被压在基字上缘、与基字**重叠**，
  不是浮在基字上方。8× 放大图可清楚看到小字与基字笔画叠在一起。
- 根因：`app/.../ui/screens/reader/components/ReaderContent.kt:855`
  ```kotlin
  val y = (anchor.top - result.size.height - RUBY_ANNOTATION_GAP_PX).coerceAtLeast(0f)
  ```
  首行的 `anchor.top ≈ 0`，减去注音高度后为负，被 `coerceAtLeast(0f)` **夹回 0**
  → 注音被画在段落顶边，与首行基字重叠。
- 更深层原因：**「注音不参与排版高度」这个降级方案本身就不成立** ——
  注音高度 ≈ `RUBY_ANNOTATION_SCALE(0.55f)` × 字号（25sp@3x ≈ 41px），
  而行间可用空隙只有约 20–35px，**即使不是首行也不够**。
  所以这不是「极端密集才出问题」，而是**每一行注音都会重叠**。
- 影响：注音可读性严重下降。Gate G5 的「注音信息可访问」勉强算过，但**观感不合格**。

**缺陷 2（宣称口径问题）：表格「列对齐」没有真正达成**

- 现象：TAB 只是展开成固定间距（两个全角空格），**不是按列宽对齐**：
  1. 第一列字数不同的行，第二列起点参差不齐（`高筋面粉    300 g` / `温水   180 ml` / `干酵母   4 g`）；
  2. 单元格换行后续行回到左边界，表格结构散掉（`过筛` 与 `后使用，避免结块` 分居两行且不对齐）。
- 结论：**「表头加粗」做到了，「按列对齐」言过其实**。真实列对齐需要按列测量宽度后补空格，
  或做真正的表格绘制（本批明确未做）。
  0.2.14 更新日志里「表格按列对齐（制表符展开为固定间距）」的措辞应改为
  「表格用固定间距分隔各列」。

**仍未验证**：长列表**跨页**编号不重置（截图停在列表第一页，0.0%）、引用（blockquote）呈现、
滑动模式下的插图、连续改字号 20 次回归、点击插图放大。

**观察（非本批引入，不应算回归）**：中英混排段落出现很大空隙 —— 读者默认 `TextAlign.Justify`
（`core/.../designsystem/reader/ReaderTypography.kt:70`），两端对齐把少量空格拉得很开。

## 5. 本批修复的缺陷（共 8 个，全部**先让测试变红再修**）

1. **`appendRange` 被误用于「显示层替代字符」**：列表前缀与 TAB 展开字符若逐个递增 rawOffset，
   会映射到**别人的**源字符上（选择/高亮错位）。新增 `appendConstRange(text, rawOffset)`。
2. **TAB 展开被 append 两次** → 显示宽度翻倍、`DisplayMapping` 边界数不匹配抛异常。
3. **列表显示层级多算一层**：`listLevel(li)` 把 `li` 自身的 `ul/ol` 也算进祖先。
   改为在 `emitList` 里对列表元素算一次、传给所有直接项。
4. **`lists +=` 丢失**：`ChapterMarkIndex.build` 里列表标注表达式结果没接住 → 列表标注全空。
5. **`DocumentTableEntry.rows` 类型理解错误**（`List<List<TableCell>>`，不是带 `.cells` 的对象）。
6. **`svgIntrinsicSize` 把百分比当数值**：`width="100%"` 被当作 100 接受，正确应回退 `viewBox`。
   百分比相对视口、不是固有尺寸 —— 已在 `svgLength` 里对含 `%` 的值返回 null。
7. **Robolectric 里 Coil 的 `ImageLoader.execute()` 死锁**（详见第 6.2 节）。
8. **【本轮真机验收新发现】「关于」页更新日志把 `**粗体**` 显示成字面星号**：
   `CHANGELOG` 的条目用 markdown 风格 `**…**` 写强调，但渲染处是**纯 `Text`**，
   于是全部历史条目都显示成 `**列表**`、`**SVG 矢量插图**`。
   修复：新增 `changelogLine()`，用 `buildAnnotatedString` 把 `**…**` 渲染为
   `FontWeight.SemiBold`；**同时修好所有历史条目**。已在真机确认（`s3.png`）。

## 6. 环境坑（必读，会再遇到）

### 6.1 ⚠️ PowerShell 5.1 回写中文会摧毁文件（真实事故，已修复）

- 用 `powershell -Command "… Set-Content … -Encoding UTF8"`（或 `Get-Content | Set-Content`）
  改 `app/build.gradle.kts`：本机 default 宿主是 **PowerShell 5.1**，它把**无 BOM 的 UTF-8 按 GBK 读**，
  中文注释变乱码再以 UTF-8+BOM 写回。
- **铁律**：
  1. 改任何含中文的文件**只用 Edit 工具或 python 字节级读写**；
  2. 必须用 PowerShell 时只能 `[System.IO.File]::ReadAllText/WriteAllText(path, text, UTF8Encoding($false))`，
     **`Get-Content`/`Set-Content` 一律禁用**；
  3. 不确定就先扫一遍：报出（a）以 `EF BB BF` 开头的 Kotlin 源、（b）含 `U+FFFD`、
     （c）含私用区字符（`U+E000`–`U+F8FF`）的文件。

> **本轮再次踩到孪生陷阱**：`adb exec-out run-as … cat <file> > local` 在 pwsh 里
> 会把二进制当文本重编码 —— 10,139,777 字节的 EPUB 被写成 19,319,790 字节的**损坏文件**。
> **二进制一律走 `cmd /c "… > file"` 或 `adb pull`。**

### 6.2 ⚠️ Robolectric 里 Coil 的 `execute()` 会死锁

- 现象：`SvgSupportTest` 用 `runTest { loader.execute(…) }` → 构建**无任何测试事件**、30 分钟不结束。
- 根因：Coil 2 的 `execute()` 依赖 `Dispatchers.Main`，而 Robolectric 默认 **PAUSED looper** → 死锁。

### 10.1 注音与基字重叠（§3.4 缺陷 1）

**根因（修正后的完整版）**：不只是 `coerceAtLeast(0f)` 的钳制，而是
**「注音不参与排版高度」这个降级方案本身容量不够**：
正文行高 = 字号 × 行距 ≈ 1.33 × 字号，基字上方只剩约 0.33 × 字号，
而注音需要约 0.55 × 字号 —— **每一行都不够**，首行最严重（被钳到段落顶边）。

**修法**：
1. 新增 `TextStyle.withRubyLineReserve()`（`ReaderMarks.kt`）：把行高撑到
   `原行高 + 0.55 × 字号 × 1.5`，并用
   `LineHeightStyle(Alignment.Bottom, Trim.None)` 让多出来的空间**全部落在基字上方**。
2. **测量与绘制共用这一个函数**：`PagedReader.measureWithMarks`（测量）
   与 `ReaderParagraph`（绘制）用同一条件（`rubyBases.isNotEmpty()`）与同一函数，
   所以分页高度与真实排版不会分叉。
3. `drawRubyUnit` 改为画在**本行行盒顶部**（`layout.getLineTop(...)`），
   并删掉 `coerceAtLeast(0f)`。
4. 注音小字显式使用**自己的行高**（`0.55 × 字号 × 1.2`）——
   继承正文行高会把它的测量高度放大成正文一整行，预留带又装不下。

### 10.2 表格列对齐：**尝试后回退，未交付**（§3.4 缺陷 2）

**尝试过的做法**：表格在内容包里是**一个**块（行用换行符、单元格用 TAB 分隔），
所以列宽可以直接从段文本算出来。据此实现：`ParagraphMarks.isTable` +
`displayWidthOf()`（东亚宽度）+ `tableColumnPadByTabOffset()`，把每个单元格补齐到该列最宽单元格，
补齐字符映射到 TAB 的源偏移。

**真机验证结果：更糟，已回退。** 补齐把第一列撑到列宽后，**宽于行宽的表格里每个单元格被迫各自换行**，
表格结构完全散掉（证据：`R:\backup-device\acceptance\v7.png`；回退后 `w2.png` 恢复正常）。

**实测数据**（本夹具第 2 章那张表）：列宽 `[8, 6, 36]`，
对齐后表头行需要 **26 个显示单位**，而一行只装得下约 **24 个**。

**根因**：正文是**分页文本流**。表格一旦宽于行宽，就不可能在流内做列对齐 ——
要么按列宽做真正的表格排版（单元格内换行），要么提供横向滚动 / 独立表格查看器。
计划书 §4.5 正是把「可单独打开横向查看 / 正文真实表格预览」列为**独立交付物**。
另外，列对齐必须在**整张表**范围内计算，而 `buildParagraphContent` 拿到的是**分页片段**，
逐片段算列宽本身也不稳。

**本版结论**：**不交付**表格列对齐，恢复「TAB → 固定两格 + 表头加粗」；更新日志也已改成不声称对齐。

**正确修法（未做，建议单独一批）**：
1. 以**整张表**为单位排版，而不是在分页片段里逐段算；
2. 用**真实字形测量**（`TextMeasurer`）而不是东亚宽度估算确定列宽；
3. 超宽表格降级为「带行列标题的逐格查看」或横向查看器（计划书 §4.5）。
